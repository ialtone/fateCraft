# 02. SillyTavern 参考与取舍

本文记录 Fatecraft 从 SillyTavern 一类角色扮演前端借鉴了什么，以及为什么没有照搬其产品边界。它用于保存架构决策背景，不是当前功能清单；当前能力以 `03-product-features.md` 和代码为准。

## 产品定位差异

SillyTavern 的中心是“用户自行配置角色、Prompt、世界书和模型以获得理想对话”。Fatecraft 的中心是“平台发布有固定规则和奖励的挑战，玩家在相同规则下参与”。两者都需要高质量长对话，但内容所有权和可信边界不同。

因此，Fatecraft 采用以下原则：

- Character、Scenario、Prompt、WorldBook 和奖励规则由管理员作为同一挑战版本发布。
- 普通用户只选择公开挑战与允许的 Persona，不读取或改写技术内容。
- 对话创建后固定版本和内容哈希，不随管理员后来发布的新版本漂移。
- 模型只能调用当前步骤开放的状态、判定、结算或领域工具；随机结果与奖励由后端验证。
- 用户自己的模型设置按账号维护；长期记忆由平台后台生成，玩家不能编辑或用它改变挑战资格。

早期文档中“用户自由管理 Prompt、角色卡和世界书”的设想已经废弃，不能据此恢复对应普通用户 API。

## 已采用的能力

### 上下文预算

完整消息历史持久化，但模型请求不会无限携带全部历史。`ContextBuilder` 按模型窗口和回复预留计算预算，再依次装配平台规则、挑战资产、当前状态、attempt 固定的长期记忆、命中的世界书和近期完整回合。

与参考产品相同的目标是：长对话不能因为历史增长而突然超过模型限制；不同之处是玩家不能为了挤入自定义内容而重新排序平台安全段。

维护要求：

- 必选 system 段不能被普通内容挤出。
- 状态、记忆策略和记忆正文应是独立可审计段。
- 最近历史从新到旧按完整回合纳入，但最终仍按时间顺序发送。
- 每次构建保存 token 分项、消息 ID 和世界书命中 ID，便于排查模型遗忘。

### Prompt 分段

Prompt 仍采用有角色、顺序、启用状态和必选标记的分段结构，这便于管理员维护系统职责、题材规则、结算安全和 Agent 工具行为。

与通用 Prompt Manager 的区别是：

- 分段属于 `challenge_version`，由管理员编辑并整体发布。
- `system_master`、`settlement_security`、`agent_tool_loop` 是发布必检的 required system 段。
- 玩家没有对话级覆盖、拖拽排序或禁用安全段的能力。
- 已发布分段不可原地修改；任何变化都需要新版本。

### 世界书扫描

世界书保留关键词触发、常驻条目、优先级、启用状态和 token 预算。这些能力适合把境界、寿元、地点和飞升路线按需注入上下文。

当前扫描源包括 attempt 固定记忆、近期未覆盖消息、本轮用户输入和当前状态字符串。常驻条目先参与，关键词条目按匹配结果激活，再根据优先级和预算裁剪。激活结果记录在上下文构建日志中。

世界书与 SillyTavern 的关键差异是所有条目都属于对话固定挑战版本。普通用户不能新增关键词、绑定其他世界书或修改正文，否则可以绕过稀有机缘与结算叙事规则。

### Character、Persona 与 Scenario

三类对象仍然分开，因为它们在上下文中职责不同：

- Character：叙事者身份、风格、首条消息和示例对话。
- Persona：玩家可选择的出身倾向和公开描述。
- Scenario：本挑战的开局环境、目标和局势。

挑战 Manifest 固定推荐 Character、Scenario 和 Prompt，并声明允许的 Persona。玩家能选择 Persona，但不能上传或编辑资产。对话只保存固定版本内的资产 ID，组合外键阻止跨版本拼装。

### 消息修正与重新生成

角色扮演对话需要编辑、重新生成和继续生成，Fatecraft 保留这些交互。所有操作仍受对话归属、active 状态和生成锁约束；编辑历史不能改变服务端已有判定流水或让 ended 对话重新结算。

### 异步记忆与上下文检查

Memory Worker 在后台自动归纳离开保护窗口的已封口回合，玩家没有生成、编辑或重试 API。当前叙事不等待它；上下文构建信息用于排查预算和裁剪。

记忆内容会进入之后新建 attempt 的上下文，但仍只是模型生成的叙事资料。后端结算只能依赖结构化状态和服务端流水，不能依赖其中的自然语言断言。

## 未采用的能力

### 普通用户模板工作台

不提供普通用户 Character、Prompt、WorldBook、Scenario 的 CRUD，也不提供对话级技术资产替换。原因不是 UI 尚未实现，而是这会破坏挑战公平性、版本可复现性和奖励可信度。

若未来要支持纯沙盒聊天，应建立无奖励的独立产品模式、路由和数据边界，不能复用挑战对话后偷偷开放编辑。

### 任意插件与脚本

不执行模型或用户提交的脚本，不通过反射把任意 action 名映射为后端函数。动作必须在后端注册表显式实现，并在 handler 内重新读取身份和服务端状态。

### 复杂扩展生态

TTS、图片生成、Gallery、第三方插件、Horde、多媒体附件和大规模 provider 特化不在当前核心范围。这些能力不能先于挑战规则、结算审计和内容发布工具的稳定性。

## 可后续评估的交互

以下思路可以改善体验，但引入时仍需服从挑战边界：

- Quick Reply：由挑战版本发布只包含叙事选择的快捷动作，不携带判定结果。
- 少量命令：例如重新生成、继续、状态、只读角色询问和上下文检查；命令仍调用有鉴权的领域接口。
- 世界书 sticky、cooldown、depth 和 inclusion group：提升复杂内容触发质量，但必须进入版本哈希。
- 向量记忆：只检索当前对话或固定挑战版本的数据，禁止跨用户污染。
- 文本后处理：仅用于展示清洗，不能从自由文本推导奖励或业务动作。

## 维护判断

评估新的参考功能时，依次回答：

1. 它属于玩家体验、管理员内容制作，还是服务端可信规则？
2. 它是否会改变挑战内容，若会，是否进入版本快照与哈希？
3. 玩家输入能否借此伪造状态、判定或结算条件？
4. 对话开始后，该功能是否会让运行规则漂移？
5. 发生争议时，是否存在可查询的数据库记录和构建日志？

任何无法清楚回答的问题，都不应仅因为参考产品已有该功能就直接加入 Fatecraft。
