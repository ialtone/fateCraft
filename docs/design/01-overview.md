# 01. 项目概览

## 产品定位

Fatecraft 是一个版本化挑战驱动的 AI 文字冒险平台。平台管理员负责设计和发布规则完整的挑战，玩家选择允许的 Persona 后进入挑战，在统一的 Prompt、世界书、判定和奖励规则下完成一局游戏。

产品的核心不是自由聊天或模板编辑，而是可复现、可审计、可版本化的挑战运行：同一挑战版本为所有参与者提供相同规则基础，每个玩家又拥有完全隔离的消息、状态、记忆和判定历史。

## 用户角色

### 普通用户

- 通过 LinuxDo 或管理员开放的邮箱方式登录。
- 查看已发布挑战的公开介绍、标签、Persona 和奖励概要。
- 创建和操作自己的挑战对话。
- 使用消息、判定、回溯、状态查看和上下文检查能力。
- 不能查看或修改技术 Prompt、世界书、角色、场景、奖励规则与平台判定配置。

### 管理员

- 具备普通用户的全部能力。
- 创建挑战包和版本草稿。
- 编辑完整版本文档，执行校验并发布不可变版本。
- 配置全局判定开关和难度。
- 必要时维护对话状态，但不能通过普通玩家接口开放这项能力。

首个创建的账号自动成为管理员，后续账号默认为普通用户。

## 核心对象

| 对象 | 作用 | 生命周期 |
| --- | --- | --- |
| `challenge_pack` | 稳定的挑战入口、slug 和公开信息 | 长期存在，可切换当前版本 |
| `challenge_version` | 一次完整规则快照 | draft 可编辑，published 不可修改 |
| `challenge_asset` | Character、Persona、Scenario、Prompt、WorldBook | 从属于一个版本 |
| `challenge_reward_rule` | 成功结局的条件与奖励公式 | 从属于一个版本 |
| `conversation` | 某玩家的一次挑战运行 | active、ended、archived、deleted |
| `conversation_state` | 当前结构化游戏状态 | 随模型动作更新并保留修订记录 |
| `roll_history` | 服务端判定结果 | 只追加，参与后续判定与结算 |
| `challenge_run` | 最终结算记录 | 每个对话最多一条 |

## 完整运行流程

```text
管理员编辑草稿
  -> 发布校验与内容哈希
  -> 挑战包指向已发布版本
  -> 玩家选择挑战和 Persona
  -> 对话固定版本、哈希和资产
  -> 后端装配当前对话上下文
  -> 模型输出叙事、状态、判定请求或动作
  -> 后端验证并持久化
  -> 达成结局后事务结算
```

每次模型生成只读取当前对话数据和固定挑战版本。管理员发布新版本不会改变已经开始的对话；如果已发布内容被绕过应用直接修改，运行时哈希校验会拒绝继续使用。

## 主要体验

- 首页：已发布挑战与当前用户的对话列表。
- 创建挑战：选择挑战、允许的 Persona 和可选标题。
- 对话：流式叙事、消息操作、结构化状态、判定结果、回溯和上下文检查。
- 设置：当前用户自己的 LLM 连接参数。
- 管理：平台判定设置和挑战版本编辑发布。

内置“飞升试炼”的境界、寿元、资源、三条飞升路线和结算规则详见 `14-ascension-trial-gameplay.md`。

## 信任边界

- 浏览器是不可信客户端，权限和归属必须由后端验证。
- 模型是不可信规则建议者，结构化输出仍需白名单、判定引擎和结算服务验证。
- 已发布内容由数据库保存，但运行时仍重算哈希以发现越过发布流程的改动。
- 用户提供的 LLM 服务可能返回非标准输出，协议解析必须失败可见、不能静默执行未知动作。
- 奖励和账号累计属于服务端权威数据，前端只展示结果。

## 技术边界

- Vue 前端负责交互和公开数据展示，不承担授权判断。
- Gin API 负责认证、参数边界、归属校验和管理员权限。
- 领域服务负责挑战、对话、状态、判定和结算规则。
- PostgreSQL 保存认证、挑战内容与全部运行时数据。
- WebSocket 只承载生成过程事件，不替代数据库事实。
- 仓库 JSON 只用于空库首次启动，不是运行时可写文件存储。

## 明确非目标

- 不向普通用户提供角色卡、Prompt、世界书或奖励规则 CRUD。
- 不允许对话创建后替换挑战版本或技术资产。
- 不维护旧数据库结构兼容层或双读逻辑。
- 不在已有挑战内容的数据库上自动导入、覆盖或迁移挑战版本。
- 当前不实现通用插件市场、多人共享同一对话或跨挑战记忆。
- 当前不把所有叙事规则都实现为确定性规则引擎；相关边界必须在玩法文档中明确。

## 部署假设

前端和后端推荐通过同一站点提供，Nginx 将 `/api` 与 `/ws` 反向代理到后端。后端连接 PostgreSQL，并从 `DATA_DIR` 读取判定配置和响应 Schema；仅当 `challenge_packs` 为空时，还会读取内置挑战材料并完成首次发布。已有挑战内容时启动过程不会读取或修改这些材料。
