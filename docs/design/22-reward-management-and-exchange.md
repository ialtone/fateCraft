# 22. 奖励管理与积分兑换

奖励是核心玩法循环：可信通关结算产生账号奖励，玩家积累点数，再兑换账号奖励或额度。管理员赠送、补偿和注册赠送是另外的获奖来源，不能冒充某局通关结果。

本文说明当前代码的账号资产、后台运营、领取和兑换行为。Campaign 局内物品带出见 [21-campaign-outcome-rewards.md](21-campaign-outcome-rewards.md)，HTTP 契约见 [10-api-websocket.md](10-api-websocket.md)。

## 管理入口与操作流程

后台独立路由 `/admin/rewards` 包含六个页签：

| 页签 | 能力 |
| --- | --- |
| 概览 | 按资产查看总余额、累计授予/消费/返还/冲正、待领取数量及兑换支出/所得 |
| 奖励资产 | 创建、编辑、启停账号货币、物品、徽章、权益、额度；查看停用影响 |
| 发奖规则 | 集中查看玩法、版本、奖励资产和计算器，跳转版本编辑器；维护注册赠送规则 |
| 用户发放 | 服务端搜索用户，查看余额，直接赠送/补偿或创建待领取奖励 |
| 积分兑换 | 创建、编辑、上下架兑换商品，查询修订和订单 |
| 记录与审计 | 按用户、资产、状态、来源和时间筛选获奖记录；查询原请求、撤销、整笔冲正、处理说明和审计 |

玩法能力页只展示已安装的可信模块。用户与权限页保留“奖励与点数”快捷入口，复用同一用户面板。普通用户不能调用管理接口；`admin` 和 `owner` 均可运营奖励，角色和账号状态变更仍只允许 owner。

配置一条“通关 → 积分 → 兑换额度”流程：先创建可叠加、可消费的 `currency` 或 `credit` 资产；在玩法草稿中绑定该资产和可信计算器，校验后发布；随后建立以该资产支付、以既有账号奖励为目标的兑换商品并上架。系统不自动替运营者决定汇率，也不额外植入一套通用积分种子。

## 资产与规则分离

`reward_definitions.id/key` 是稳定账号资产身份。更名、说明、图标、排序和 featured 调整不拆分余额，也不改写历史获奖快照。存在玩法、余额、账本、获奖记录、注册规则或兑换商品/修订引用后，不允许改变 key、kind、stackable、consumable；平台剧情改写额度的语义始终固定。非叠加奖励不能消费。

资产停用禁止新管理员发放、新注册赠送、新兑换和新增规则引用/发布；已经发布的固定玩法、已产生的待领取资格继续按原快照履约，已有余额仍可用于原平台消费。停用对话框显示规则、待领取和兑换商品影响；若当前注册规则使用该资产，必须明确确认同时停用注册赠送。重新启用资产不会自动启用注册规则或已下架商品。

玩法奖励属于 `challenge_reward_rules`，随挑战版本固定并进入内容哈希。后台支持 `core.fixed`、`core.state_multiplier`、`campaign.extract_item_stack` 参数表单，计算逻辑仍只由后端可信模块执行。已发布版本只读，编辑必须创建草稿并发布，不能在奖励中心绕过版本控制。

`registration_reward_rules` 只追加修订，最新一行是当前规则。初始配置为新账号获得 10 份 `fatecraft.message-rewrite-credit`；管理员可以更换资产、数量或停用。创建账号、消费验证码/邀请码、应用注册奖励在原认证事务中执行，历史赠送记录保留规则修订。

启动仅在无挑战包时初始化官方内容；已有内容不会被重启覆盖。显式导入前读取奖励差异、共享引用和前后规则预览，确认时提交 `preview_token`。服务端在配置锁中重新计算并核对预览，变化后要求重新确认；资产语义冲突拒绝整包导入。

## 获奖记录与账本

`reward_records` 保存一份获奖资格及其结果：用户、资产、来源、稳定来源键、不可变展示快照、数量、发放方式、状态、实际账本关联和完成时间。数据库同时约束 `source_key` 和 `(player_id, source_type, source_id, reward_definition_id)` 唯一。来源记录、余额、账本与原业务状态在同一事务提交。

| 状态 | 含义 | 余额与后续动作 |
| --- | --- | --- |
| `pending` | 管理员创建待领取资格 | 不增加余额，可由本人领取或管理员撤销 |
| `granted` | 已实际到账 | 关联唯一 grant 流水，不可再次领取 |
| `skipped` | 已拥有非叠加资产，或可信规则算出零数量 | 保存 `already_owned/zero_quantity`，无 grant 流水 |
| `cancelled` | 待领取已撤销 | 无余额变化，展示公开撤销原因，不可恢复领取 |

整笔冲正通过 `reversal_ledger_id` 关联追加的反向流水，不增加第二套主状态，不重新开放资格。界面和状态筛选将有关联的记录显示为“已冲正”。单条记录的 `quantity` 是获奖数量；只有 `granted` 有真实授予量，pending/skipped/cancelled 当前到账量为零。

`reward_ledger` 只追加 `grant/consume/refund/reverse` 四种操作。余额公式为 `granted_total - consumed_total + refunded_total - reversed_total`，各累计值独立保存。消费返还只能关联已有的原消费，整笔冲正只能关联原授予；每笔原流水最多各有一次对应操作。返还不产生新的获奖资格。

数量、单用户余额和累计数量限于 `0..9007199254740991`；管理员发放与兑换必须是正整数，不支持小数。跨用户概览总数可能超过 JavaScript 安全整数范围，因此 API 用十进制字符串返回，各资产不相加。概览中的累计授予包含兑换所得、累计消费包含兑换支付，兑换列为其中的分项。

## 用户搜索、发放与处理

搜索在数据库执行：UUID 精确匹配；包含 `@` 的查询按完整邮箱不区分大小写匹配；其他查询按用户名/显示名称不区分大小写、字面包含匹配，转义 `%`、`_`。分页返回 `{users, has_more}`，页面必须使用 `users` 数组，不能把响应对象当成账号列表。提交绑定选中的用户 ID，不依赖显示昵称或当前列表位置。

管理员发放请求包含 `request_id`、资产、正整数数量、`gift/compensation`、`direct/claim`、内部原因和可选公开说明。预览展示账号、资产、数量、用途和发放方式；提交后按实际状态展示结果。事务再次检查管理员权限、目标 active 状态和资产可用性。已拥有的非叠加奖励合法跳过，不能误报新增到账。

同一 request ID、相同内容返回原结果；更改目标、数量、资产、用途、方式或说明后复用 ID 返回冲突。响应丢失时查询原请求或重试同次发放，暂未查到不代表事务已经失败。已成功请求的重放不受后续资产/账号停用影响；读取 API 本身仍需有效登录和权限。

普通用户只能读取和领取自己的记录。领取与撤销使用记录行锁竞争，最多有一个终态变更成功；账户停用后不能新领取。首次领取通过统一入账函数处理，重复领取返回原结果。页面同步刷新余额、获奖列表、流水和顶栏额度。

管理员可撤销 pending、添加内部处理说明，或对余额足够的可叠加 currency/credit 作整笔冲正。不可叠加资产、物品类、兑换来源不能通过该入口冲正。冲正仅扣回账号资产，不恢复 Campaign 局内来源物。内部管理原因、操作者、管理请求哈希和审计只向管理员公开；用户只看到公开说明和撤销原因。

每次管理变更与 `admin_audit_logs` 同事务保存。该系统没有“伪造来源补写漏发”的接口；原业务失败应检查可信来源和事务结果，额外补偿必须使用独立 `admin_grant` 来源。

## 积分兑换

首期仅支持账号资产之间的兑换。支付资产必须是可叠加、可消费的 currency/credit，所得是不同的既有账号资产；非叠加目标每份数量和兑换份数均只能为 1。没有局内物品发货、现金、外部履约、限量库存、兑换次数上限或自动兑换汇率。

`reward_exchange_offers` 保存当前价格、所得、上架状态、排序和修订；每次保存同时追加不可变 `reward_exchange_revisions` 和管理审计。编辑须带原 revision，拒绝覆盖其他管理员刚保存的版本。

玩家提交 `{request_id, offer_id, revision, units}`。事务依次核对已提交请求、当前商品修订与可用性、用户状态，按稳定资产 ID 顺序锁支付与目标余额，检查目标所有权，再扣支付资产、发目标奖励、保存不可变订单。任一步失败整体回滚。目标已拥有时拒绝兑换并保留点数，不能套用普通赠送的“跳过但成功”语义。

订单保存商品名称、说明、单价和两端资产快照，关联支付 ledger 和所得 reward record。同次请求重复提交只返回同一订单；同 ID 不同内容冲突。过期价格、资产停用、商品下架、余额不足均不扣分。商品改名/调价不改变旧订单。

玩家页面展示商品与确认预览，并支持原请求查询、同次重试、订单历史。尚未确认的兑换保留请求 ID；同一浏览器标签内刷新后从按账号隔离的 sessionStorage 恢复，数据库结果始终是权威。订单成功后刷新账号资产与记录。首期没有兑换退款接口，也禁止通过通用返还或管理员冲正只退一边。

## 事务与维护边界

统一业务函数位于 `internal/storage/reward_records.go`、`reward.go`、`reward_configuration.go`、`reward_exchange.go`；原结算事务传入同一 GORM 事务，不另行提交。注册、自动通关、Campaign、管理员赠送、领取和兑换所得共用同一入账规则。

请求锁与数据库唯一约束负责幂等；配置修订使用配置 advisory lock，独立发放/兑换使用共享配置锁；多资产结算与兑换按资产 ID 升序锁余额。余额不会为负，管理审计失败会回滚相应变更。`client` 对话不能生成通关获奖记录、不能扣带出来源；账号仍可接受独立注册赠送/管理员赠送，并使用合法已有余额兑换。

新项目全部结构、索引、触发器和初始注册规则写在 `backend/migrations/00001_init.sql`，没有 00002、历史回填、双写或旧接口兼容层。已经执行过旧版 00001 的数据库不会因再次运行 `migrate up` 自动补表；验证应使用空 schema。不要为应用新版基线而自动删除用户数据。

暂不实现冻结、有效期/延期、批量领取、部分冲正、资产独立发布版本、异步发货或通用任务补发平台。
