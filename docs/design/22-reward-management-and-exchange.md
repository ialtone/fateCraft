# 22. 积分、剧情改写次数与奖励管理

## 玩法模块接入

新增模块沿用两项账号资产及本文账本，不把现金、食水、遗物、弟子贡献或宗门库存变成新账号货币。模块只返回可信结局，积分由平台按固定内容结算；七个新示例默认 0 分，管理员需根据真实游玩成本单独配置正式版本。

显式改写可恢复 Campaign 完整检查点，但账号奖励与账本不随之回档。改写成本与 client 路由规则继续有效，非零/零/直连和故障账本验收见[模块验证记录](gameplay-modules/validation.md)。

## 业务闭环

可信通关后积分自动到账，用户积攒积分兑换剧情改写次数，平台改写按次扣除。账号系统只保留两个固定余额：

| 项目 | 固定 key | 获取与用途 |
| --- | --- | --- |
| 积分 | `fatecraft.points` | 通关、玩法阶段、注册赠送、管理员发放；支付兑换商品 |
| 剧情改写次数 | `fatecraft.message-rewrite-credit` | 兑换、注册赠送、管理员发放；平台改写消费 |

身份、名称与单位由平台代码定义，服务端和数据库均限制为这两项。后台不能创建其他账号货币、物品、徽章或权益。所有发放直接到账；局内库存、任务奖励、市场和成长仍属于原玩法，不自动折算为账号积分。

## 通关积分与初始配置

每个结局配置一个 `reward_points`，范围为 0–9007199254740991 的整数，省略视为 0。积分属于固定玩法版本，进入内容哈希；编辑已发布玩法必须创建草稿并重新发布。单局和 Campaign 均在可信结局事务内发放，同一结算对象只发一次。0 积分正常完成，不创建零金额账本；结局事实保存实际所得。

`client` 直连模式不发通关积分，结局、事件和快照带 `rewards_disabled_reason=client_llm_route`，显示原因和实际 0 积分。独立注册赠送、管理发放和已有余额不受此规则影响。

开发初始值集中在内置包和 [00001_init.sql](../../backend/migrations/00001_init.sql)：

| 配置 | 初始值 |
| --- | --- |
| 正统渡劫 / 虚空飞升 / 仙缘飞升 | 300 / 200 / 150 积分 |
| 青河三个阶段 | 各 100 积分，共 300 |
| 执掌天关 / 携律远行 | 终局各 700；含阶段完整通关各 1000 |
| 其他未配置结局 | 0 积分 |
| 注册赠送 | 0 积分、10 次剧情改写 |
| 商品“剧情改写 1 次” | 100 积分兑换 1 次，上架，每人兑换不限 |

青河阶段依据固定版本条件自动发放，receipt 与账号账本不随回档恢复，0 分和直连明确记录实际发放；后台显示阶段加终局的总预算，协议见 [21 阶段与终局](21-campaign-outcome-rewards.md)。这些是经过离线样本验证的初始配置，真实玩家与模型节奏仍待试玩。重启不覆盖管理员配置；商品初始化修订的操作者为空，页面显示“系统初始化”，无需创建假用户。余额缺行读取为 0，只有实际入账才产生余额。

## 页面与操作

玩家 `/rewards` 顶部固定显示两项余额，小 Tab 顺序为 **积分兑换、兑换记录、收支记录**，默认积分兑换。积分兑换页顶部是积分 CDK 输入框。商品卡片展示名称、说明和积分价格（站内奖励另显示所得次数）；右下角始终显示“商品剩余 X / Y”，左下角仅在设置上限时显示“您可兑换 剩余 / 上限”。库存为 0 时按钮显示“已售罄”并禁用，额度用尽显示“已达上限”。可选份数上限 = min(剩余额度, 剩余库存, 余额可买份数)。成功后弹出“兑换成功”：CDK 商品显示 CDK 与复制按钮，使用教程非空时渲染为 Markdown 展示；兑换详情可通过订单快照重新打开。

“查询兑换结果”放在兑换记录内的独立弹窗。商品列表下不堆放订单或查询结果。收支按项目、来源、时间筛选，列表和订单使用独立游标分页；切换 Tab 保留已加载内容和筛选。

后台 `/admin/rewards` 分为：

| 小 Tab | 子页与操作 |
| --- | --- |
| 积分规则 | 通关积分：按玩法和版本查看结局积分、跳转版本编辑；注册赠送：独立编辑两项数量 |
| 兑换商品 | 新建时选择类型（CDK / 站内奖励，创建后不可改），配置名称、说明、价格、所得次数（站内奖励）、每人上限、排序、上下架和 Markdown 使用教程（左侧输入、右侧实时预览）；“库存”弹窗粘贴 CDK（每行一个，重复拒绝并列出）或按数量添加站内奖励库存，按状态筛选、明文查看 CDK，批量移除仅限可兑换库存。商品只能下架，不能删除 |
| 工单 | 开关控制玩家能否提交（默认开启）；按状态筛选，同意退款或填写原因驳回 |
| 积分 CDK | 按名称、面值、数量（1–1000）、有效期（1/3/7/15/30 天，默认 7）生成批次，查看批次兑换进度和每个 CDK 的使用者 |
| 用户与记录 | 用户查询、收支记录、兑换订单、管理操作四个子页，默认用户查询 |

用户查询支持用户 ID、完整邮箱、用户名/显示名称的服务端搜索与分页。选中用户后显示两项余额，子页只有“发放”和“收支”。用户与权限页复用同一面板。

管理员发放需选择项目、填写正整数数量、必填内部原因和可选公开说明。确认窗口显示目标用户与金额，服务端根据路径用户 ID 和当前认证身份执行。`admin`、`owner` 可管理，普通用户只能访问本人余额和记录；内部原因、操作者、请求指纹及元数据不会进入玩家账本响应。

误发时在原管理员发放的收支详情填写原因，确认“撤回本次发放”。只能整笔追加反向流水，每笔最多一次；余额不足拒绝，不允许负数发放或直接改余额。仅管理员发放支持撤回，通关和兑换所得不提供此入口。

注册规则只保留赠送积分和赠送次数，两项都为 0 即关闭赠送。保存需带当前规则 `id`，过期配置拒绝覆盖。用户保存实际采用的 `registration_reward_revision`，即使赠送为 0 也标记已处理；创建用户、消费验证码/邀请码、两项入账与修订标记共同提交。重试不会重复赠送或套用新规则。

## 兑换与异常恢复

兑换商品用积分支付，分两类：`kind=reward` 站内奖励（获得剧情改写次数），`kind=cdk` 发放 CDK。价格和所得次数必须是正安全整数；`max_redemptions_per_user` 为 0 表示不限，正整数表示同一账号对同一商品的累计兑换份数上限。服务端核对 `revision`、用户状态、商品状态和剩余额度，再检查乘法、余额与累计值上限；过期价格要求刷新重新确认，不自动按新价成交。

每人额度按该玩家该商品全部成功订单的 `SUM(units)` 计算，跨越所有历史修订，不按月份或配置更新时间重置；失败或回滚订单不占额度。一笔订单必须整体落在剩余额度内，超额整笔返回 409 `exchange_limit_reached`，不拆单、不部分成交。提高或取消上限不改写历史订单；降低到已兑换数以下时不撤销已有奖励，剩余额度为 0，直到配置提高。切换上下架不重置已用额度，已成功订单的查询和原样重放也不受新限额影响。

扣积分、加次数、两条账本和订单在同一事务成功；额度校验在扣积分、发放次数和写订单前完成。同一账号不同请求的并发兑换由用户行锁串行校验，两个事务不能同时看到旧额度而越限。订单保存商品名称、说明、成交单价、份数和合计快照，引用不可变商品修订及 `cost_ledger_id`、`reward_ledger_id`。修改商品不改写历史订单。兑换的退款只能经工单审批（见下节）；改写失败返还及管理员撤回不能用于兑换的任意一侧。

发放、撤回、兑换均使用稳定请求 ID。原样重试返回原结果，相同 ID 换参数报冲突。查询与重放仍需当前权限；已成功兑换在商品下架后仍可恢复原结果，新兑换则被拒绝。

网络失败不能当成未成交。玩家按账号隔离保存 sessionStorage 待确认请求，支持查询或原样重试，切换 Tab、页面刷新后可恢复；查询旧订单不能清除另一笔待确认请求。管理员发放按操作者和目标用户隔离保存待确认请求；撤回弹窗在结果未确认前保留同一请求，支持查询恢复和重试。

未确认兑换保留原商品快照，刷新列表不会用新价格、已用额度或下架状态覆盖该快照；原样重试不被最新余额和剩余额度阻止，服务端仍负责核对原请求。新兑换的份数同时受积分余额、剩余额度和安全整数范围约束。直接兑换、查询本次结果及在订单页确认原请求成功后，都重新读取商品额度；已有读取未结束时，在它结束后再读一次，避免使用成交前结果。超额拒绝并不代表剩余额度为零；自动刷新失败时明确显示失败，不提示已刷新成功。

## 库存、工单与积分 CDK

每个商品的库存逐份保存在 `reward_exchange_stock`，状态为 `available / redeemed / removed / voided`。CDK 商品每行一个 code，`(offer_id, code)` 唯一，粘贴内重复或与已有库存重复时整批拒绝并返回 `duplicates`；站内奖励按数量生成空 code 行。展示口径：总数 = available + redeemed，剩余 = available；已移除、已作废不计入。每人已兑换份数按该玩家 `redeemed` 库存计算，因此退款作废后额度自动恢复。

兑换在同一事务内用 `FOR UPDATE SKIP LOCKED` 取所需份数的可用库存，不足整笔返回 409 `exchange_stock_insufficient`（“库存不足，请刷新后重试”），不部分成交；之后扣积分、站内奖励发放次数、写订单并把库存标记为 `redeemed`。订单快照保存 kind、教程和发放的 CDK，CDK 商品订单 `reward_ledger_id` 为空。错误码：`exchange_limit_reached`、`exchange_stock_insufficient`、`exchange_offer_disabled`、`exchange_revision_conflict`。

CDK 订单可在兑换详情提交工单，每笔订单只有一张工单（`order_id` 唯一）；驳回后玩家可补充说明重新打开，记录只追加到同一工单。管理员同意后在同一事务关联原积分消费写 `refund`（来源 `reward_exchange_refund`）、库存置 `voided`、工单置 `refunded`；驳回必须填写原因。工单开关关闭时拒绝新提交（`exchange_tickets_disabled`），已有工单仍可处理。

积分 CDK 为 32 位随机码，按批次生成并设置过期时间。玩家兑换时锁定 CDK 行，校验存在、未使用、未过期，且同一玩家每批次只能兑换一次（`points_cdk_unknown / used / expired / batch_redeemed`），成功后写 `grant`（来源 `points_cdk`）。

教程与工单说明以 Markdown 文本保存，编辑时为文本框加实时预览；所有展示（成功弹窗、兑换详情、工单记录）统一经 `renderMarkdown`（marked + DOMPurify）净化后渲染，不执行脚本。

## 记账与改写消费

所有路径复用 `internal/storage/reward.go`：`grant` 为收入，`consume` 为支出，`refund` 为返还，`reverse` 为撤回。余额及授予、消费、返还、撤回累计值均为非负安全整数，余额满足四项累计值的净额关系。

账本来源唯一身份为 `(player_id,reward_key,operation,source_type,source_id)`，另外约束 `idempotency_key` 和管理员 `request_id` 唯一。来源与请求锁防止重试重复入账，跨余额操作按固定 key 顺序加锁；管理发放按用户 ID 顺序锁定操作者与目标，配置与兑换按配置锁、用户锁、余额锁顺序执行。

账本 `balance_after` 保存本次变动后的余额；公开说明与内部原因分字段保存。管理员来源必须有操作者、请求 ID、指纹和内部原因。`refund/reverse.related_entry_id` 关联原消费/授予，部分唯一索引限制各处理一次，触发器检查用户、项目、金额、原操作与来源。账本、注册修订、商品修订、订单只追加，拒绝修改或删除。

剧情改写沿用平台策略，每次消费 1 次。改写和重新生成按每次操作请求作为扣费来源，同一对话的后续新操作正常计费，同次重试不会再次扣除。只有原消费存在且满足“尚未提交任何动作就失败或取消”的条件，才关联原流水返还一次；提交动作后叙事失败不返还。直连改写/重新生成不扣费。返还不能用于积分兑换支付。

管理员操作在同一业务事务写入 `admin_audit_logs`；审计写入失败则业务回滚。详情从账本读取操作者与内部原因，管理操作子页展示发放、撤回、注册规则、商品配置及内置导入审计。

## 数据、内容与接口

数据库保留 `player_reward_balances`、`reward_ledger`、`registration_reward_rules`、`reward_exchange_offers/revisions/orders`、`reward_exchange_stock`、`reward_exchange_tickets/ticket_entries`、`points_cdk_batches/points_cdks` 和单局结算投影；工单开关存于 `system_settings.exchange_tickets_enabled`。结局积分直接存入 `challenge_outcome_rules.reward_points`。不另建积分钱包，不保留通用账号资产定义、领取资格或奖励计算器。

包只在 `pack.json.outcomes` 填写积分。导入器拒绝旧 `rewards.json`，Manifest 和版本保存拒绝旧 `reward_rules` 等未知字段；奖励 API 拒绝旧资产 ID、领取方式等参数。入口 `reward_balance` 条件和能力成本只接受两个固定 key。

接口与 DTO 见 [10 API](10-api-websocket.md)，模型与约束见 [07 数据库](07-database-postgresql.md)，Campaign 见 [21 终局积分](21-campaign-outcome-rewards.md)。

## 新项目基线与验收边界

本次结构直接并入 `00001_init.sql`，没有新增 00002、兼容接口、旧币折算或历史回填。已执行旧 00001 的数据库不会自动获得修改。Goose 基线 Down 仍明确拒绝回滚；不能通过改版本号、自动清库或重写真实账本来适配。验证应使用专用数据库的空 schema。

代理完成 Go 本地测试、静态检查、前端类型检查/生产构建及已有页面结构测试。**真实 PostgreSQL 和浏览器验收由用户执行，本地跳过不代表集成验收通过。** 在专用环境配置 `FATECRAFT_TEST_DATABASE_URL` 后，于 backend 执行 `go test ./...`，现有 `testdb` 工具会创建隔离 schema。

待用户验证：

- 空 schema 完整执行 00001，初始两项规则/商品可用，重启不覆盖；不可变、关联及余额约束生效。
- 注册默认 10 次，配置 0 正常生效、失败整体回滚、并发重试不重复赠送。
- 单局与 Campaign 固定积分、0 分、重复结算及失败回滚；原局内任务/消耗不受影响；直连不发积分。
- 管理员查找用户、两项直接发放、误发撤回、余额不足拒绝；并发、自我发放、停用账号、权限撤销与隐私隔离。
- 兑换价格过期、下架、余额不足、溢出、不同请求并发、同请求重试及订单失败回滚；账本净额与两项余额一致。
- 每人限额按份数累计且跨修订：不限、正整数、达到上限、超额整笔拒绝、提高/取消/降低上限和上下架不清除历史计数；其他商品与他人额度隔离；最后额度并发竞争最多一笔成功；相同 request_id 重放不重复计数。
- 剧情改写正常扣次、符合条件时返还一次、提交动作后不返还、直连不扣费。
- 浏览器大小屏 Tab、分页、筛选、确认、加载失败重试、余额同步；跨账号隔离、刷新恢复及历史查询不清除另一笔待确认请求。

后续功能应先有真实消费接口与用途，再扩展兑换；当前不包含反向兑换、用户转账、现金支付、到期失效、冻结、账号物品商城或成就系统。

## 玩法包交换与版本管理

玩法积分流水 metadata.gameplay_source 为服务端可信发放快照，列表/详情展示实际版本与阶段/结局，支持 pack_id、version_id 筛选；退役版本仍可查询。来源链接查看固定快照，不授予读取用户私人正文的权限。

完整协议见 [27 玩法包交换与版本生命周期](27-gameplay-package-exchange-and-versions.md)。
