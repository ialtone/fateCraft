# 11. 路线图与工程边界

路线图按风险和依赖排序，不代表承诺日期。每项只有在代码、数据库、管理流程、测试和文档同时满足验收条件后才算完成。

## 当前基线

项目目前已经形成以下可继续演进的基线：

- LinuxDo OAuth、默认关闭的邮箱认证和 14 天服务端会话。
- user/admin 角色、对话归属检查和管理员路由隔离。
- PostgreSQL 挑战包、不可变版本、版本资产与结构化奖励规则。
- 官方 JSON 在空库首次启动时自动初始化；已有挑战内容时服务启动不读取或覆盖版本。
- 对话固定挑战版本、资产 ID 和内容哈希，运行时从数据库装配。
- 模型结构化信封、状态白名单、两阶段判定和服务端判定流水。
- 结局动作在回复落库前按固定版本预校验境界和精确判定证据，无效候选自动丢弃并纠错一次；通过后在唯一事务中复核、记账和结束对话。
- 普通用户挑战入口、Persona 选择、对话流程与管理员版本 JSON 管理。

“已具备基线”不表示玩法全部由硬规则执行。当前修为状态、寿元消耗、具体任务链和局内灵石增减仍由模型提出；飞升结算额外要求服务端境界等级和逐级成功判定证据。具体边界见 `14-ascension-trial-gameplay.md`。

## P0：结算可信度

当挑战奖励具有账号价值时，最优先工作是减少模型叙事对资格判断的影响。

### 唯一雷劫波次（1.0.0 基线已完成）

奖励条件已改为精确成功判定类型集合。正统飞升逐一要求第一波至第九波，查询使用精确匹配并去重；重复第一波和相似前缀不能满足结算。

已完成：

- 官方内容固定九个不可互换的判定类型。
- 发布校验拒绝空、重复或类型错误的 `required_successful_rolls`。
- 结算只接受当前对话中每个必需类型的成功流水。

剩余增强：若未来允许失败波次重试、作废旧结果或多套劫云序列，再把判定类型升级为结构化 `event_key` 或 `sequence_key + step`，显式表达序列实例和重试策略。

### 境界与关键物品资格（第一阶段已完成）

1.0.0 已实现境界字符串归一化等级、三条路线的最低等级、逐级突破成功证据，以及仙缘路线的 `仙缘获取判定`。这些检查在候选回复落库前和事务提交时共用同一套逻辑；同一回复写入的新境界或飞升符不能为自身补资格。

仍需完成：

- 关键物品使用稳定 ID，不以叙事名称判断。
- 把修为和关键物品状态从 AI 状态补丁迁移到不可伪造的服务端事件流水。
- 为隐藏任务建立服务端任务节点，避免只凭模型请求一次 `仙缘获取判定`。

验收：当前阶段要求仅编辑摘要、结局文本、单次 state update、相似判定名或复用其他对话流水均不能绕过结算；最终阶段还要阻止模型在更早回合无依据地抬高境界或请求关键事件。

### 局内经济账本

当前奖励基数读取 `attributes.灵石`。它受到状态白名单保护，但仍由模型提出增减。

目标：

- 灵石获得和消耗改为服务端经济事件。
- 每笔事件记录来源、原因、关联消息或判定、变化前后余额。
- 结算从账本余额读取，并校验余额非负与事件幂等键。
- 管理员能查询单局经济明细和最终计算过程。

验收：模型一次性写入巨额灵石、重复消费事件或重放生成结果不能改变可信余额。

## P1：内容管理可维护性

### 分资源编辑器

当前完整 JSON 编辑器适合验证底层模型，但不适合长期运营。

目标：

- Manifest、Character、Persona、Scenario、Prompt、WorldBook 和奖励规则分区编辑。
- 表单提供字段说明、引用选择器、JSON 预览和未保存提示。
- Prompt 分段与世界书条目使用稳定 ID，支持排序但不允许破坏必选段。
- 保留完整 JSON 导入导出作为管理员高级入口。

验收：管理员无需理解数据库 UUID 即可复制版本、修改一项资源并发布；所有表单仍走同一领域校验。

### 版本差异与发布报告

目标：

- 展示草稿与当前发布版本的 Manifest、资产和奖励规则差异。
- 发布校验按字段和资源返回结构化错误，而不是单段错误文本。
- 发布确认页突出奖励、必选 Prompt、安全段和 Persona 范围变化。
- 保存发布者、发布时间、哈希和可读变更说明。

验收：维护者能在发布前明确回答“哪些玩家规则发生了变化”。

### 生命周期与使用量

目标：

- 支持挑战下架和版本 retired 流程。
- 展示每个版本的新建对话数、active 对话数和结算数。
- 禁止删除仍被对话或结算引用的版本。
- 为旧版本修复提供“复制为新版本”而非原地修改入口。

## P1：测试与可观测性

### PostgreSQL 集成测试

补充真实数据库测试，覆盖：

- 草稿保存与发布并发锁。
- 哈希稳定性和同版本内容冲突。
- 对话固定版本及组合外键。
- 两个请求同时结算同一对话时只记账一次。
- 用户跨对话、跨版本和跨玩家访问被拒绝。

单元测试不能替代这些事务与约束场景。

### 审计与监控

目标：

- 记录认证失败、管理员内容变更、发布、结算拒绝和哈希不一致事件。
- 指标覆盖生成耗时、上游错误、上下文 token、判定分布和结算结果。
- 日志不包含 Cookie、OAuth token、密码、LinuxDo Secret 或 LLM API Key。
- 为异常奖励、重复失败和上游费用突增配置告警。

### 备份恢复

目标：

- 明确 PostgreSQL 自动备份、保留周期和异地副本。
- 定期在隔离环境演练恢复，而不是只确认备份文件存在。
- 恢复后校验用户、挑战哈希、active 对话和结算流水的一致性。
- 把恢复时间目标和可接受数据丢失窗口写入部署文档。

## P2：认证与账号安全

- 邮箱验证：注册后必须验证邮箱，验证令牌只保存哈希并短期有效。
- 密码重置：一次性令牌、频率限制、成功后撤销旧会话。
- 设备会话：列出活跃设备、单独撤销或全部退出。
- OAuth 绑定：明确已有邮箱账号与 LinuxDo 身份的安全合并流程，禁止只凭相同邮箱自动合并。
- 密钥保护：评估用户 LLM API Key 的应用层信封加密和主密钥轮换。
- 限流：覆盖登录、OAuth flow、摘要生成、对话生成和管理员发布接口。

邮箱认证正式开放前，至少完成邮箱验证、密码重置、限流和审计；否则继续保持服务端开关关闭。

## P2：玩法质量

### 服务端规则引擎

逐步把高价值条件从自然语言迁移为版本化结构规则，优先顺序是飞升资格、关键物品、寿元归零和灵石账本。叙事细节仍由模型负责，不需要把所有剧情写成硬编码状态机。

### 平衡数据

管理员应能按挑战版本观察：

- 平均回合数和寿元消耗。
- 各境界到达率、突破尝试与成功率。
- 三条路线的选择率、成功率和奖励分布。
- bad/neutral 结局原因。
- 判定基础值、最终概率与实际结果的偏差。

平衡调整必须发布新版本，并在变更说明中记录数据依据。

### 内容回归测试

为官方挑战建立固定场景：开局初始化、筑基成功/失败、寿元警告、九波雷劫、虚空穿越、飞升符、坐化和寿元耗尽。测试既检查 JSON 结构，也检查奖励 key、结局标题和状态路径。

## 暂不进入核心范围

- 普通用户自由编辑 Prompt、世界书、Character 或 Scenario。
- 把已发布挑战版本恢复为可写草稿。
- 用摘要或模型自然语言直接授予奖励。
- 插件执行、任意脚本动作和未隔离的跨对话向量记忆。
- 在没有审计和成本边界前扩展多媒体生成。

若未来增加无奖励沙盒模式，应作为独立领域设计，不降低挑战模式的权限与结算约束。

## 每阶段完成定义

一个路线图条目完成时至少需要：

1. 数据模型与领域边界明确，失败和并发路径有定义。
2. 后端鉴权、事务和数据库约束已实现。
3. 前端提供完整操作、加载、空数据和错误状态。
4. 单元或集成测试覆盖主要成功与越权路径。
5. 初始化、部署和回滚方式可执行。
6. 对应设计文档、玩法规格和 API 契约同步更新。

只完成界面或只在 Prompt 中增加一句规则，都不能视为平台能力完成。
